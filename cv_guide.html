Page 1: System Architecture Overview

The portfolio uses ASP.NET Core MVC for its pages and request handling. ASP.NET Core Identity manages admin sign-in, while SQLite stores Identity records and editable portfolio entries. Starting profile and education data are seeded into SQLite, then managed from the admin dashboard.

[ Visitor or Admin Browser ]
                │
                ▼ (Request to MVC route)
[ Home / Admin Controller ] ──► [ Services and EF Core ]
                │                                │
                ▼                                ▼
[ SQLite app.db ] ◄──(Entity Framework Core)──┘
[ Admin Login ] ──► [ ASP.NET Core Identity ] ──► [ Auth Cookie ]

Core Components:

  • Controllers: The Home controller loads public portfolio records and processes contact messages; the Admin controller handles sign-in and portfolio management.
  • ASP.NET Core Identity: Verifies passwords, stores password hashes, manages roles, and issues the authentication cookie.
  • SQLite (`app.db`): A self-contained database storing Identity data and portfolio records. SQLite data is not encrypted by default; Identity hashes passwords rather than storing them as plain text.

Database Setup & EF Core Configuration

Page 2: Connecting C# to SQLite

Entity Framework Core (EF Core) acts as an Object-Relational Mapper (ORM), letting us write C# code instead of raw SQL queries to interact with our database.

1. Connection String (`appsettings.json`)

{
  "ConnectionStrings": {
    "DefaultConnection": "Data Source=app.db"
  }
}

2. Database Context (`Data/ApplicationDbContext.cs`)

The context inherits from IdentityDbContext, which provides Identity tables, and also exposes portfolio tables for Projects, Skills, Experiences, Certifications, Education, and the single editable Site Profile.

using Microsoft.AspNetCore.Identity.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore;
using BeginnerMvc.Models;

namespace BeginnerMvc.Data
{
    public class ApplicationDbContext : IdentityDbContext
    {
        public DbSet<Project> Projects { get; set; }
        public DbSet<Skill> Skills { get; set; }
        public DbSet<Experience> Experiences { get; set; }
        public DbSet<Certification> Certifications { get; set; }
        public DbSet<Education> Education { get; set; }
        public DbSet<SiteProfile> SiteProfiles { get; set; }

        public ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
            : base(options)
        {
        }
    }
}

The migration files describe database structure changes. The app applies pending migrations automatically during startup with Entity Framework Core, then seeds the initial Admin account, profile, and education records when they are missing. The database file is data storage; it is not a compiled program binary.

Admin Credentials & User Secrets

Page 3: Keeping local credentials out of source files

The Admin account seeder reads its email and password from application configuration at runtime. For local development, provide these values with .NET User Secrets using the dotnet user-secrets command. The contact email service also reads its Resend API token and sender address from environment configuration.

Configuration keys

  • AdminSettings:Email
  • AdminSettings:Password
  • RESEND_APITOKEN (environment variable)
  • Resend:FromEmail (set as Resend__FromEmail environment variable)

Use dotnet user-secrets set to set each key on your development machine. Keep the actual values out of C# code, HTML guides, settings files, and source control. This guide covers local development; deployment configuration belongs to the separate hosting lesson.

ASP.NET Core Identity hashes the password when it creates the account. The seeder needs the configured values only when it checks for or creates the initial Admin account.

Authentication & Future Roadmap

Page 4: Login Verification & Next Steps

When an admin signs in, Identity checks the submitted password against its stored hash, then issues an authentication cookie. Admin routes require membership in the Admin role.

Login Form Input ──► SignInManager ──► Matches Hashed Password in SQLite ──► Issues Auth Cookie ──► Admin Dashboard

Current Features:

  • ASP.NET Core Identity handles sign-in and role-based admin authorization.
  • Five failed password attempts lock the account for five minutes.
  • Admin pages manage Projects, Skills, Experiences, Certifications, Education, and the public Site Profile.
  • The public home page reads these sections from SQLite. Profile settings control the Home, About, and Contact details, plus the photo and CV paths.
  • The contact form validates on the server and sends through Resend when its API token and verified sender are configured. The recipient address is currently set in Services/ResendEmailService.cs.
  • The startup seeder creates the Admin role and initial account when needed; local credentials belong in User Secrets and must not be committed to source control.

Contact Form Spam Protection

Page 5: What the rate limit and honeypot do

The contact form has two lightweight checks. The rate limit slows repeated submissions from one detected IP address. The honeypot looks for basic bots that automatically fill every form field. Both checks run on the server.

1. Rate limit: slow down repeated requests

The app allows up to five POST requests per detected IP address in a 15-minute window. The sixth request in that window receives HTTP 429 Too Many Requests and a message to try again later. The limit counts requests before the form is processed, including requests with missing or invalid form data.

This limit is stored in the running app's memory. Restarting the app resets it. The local check sent six empty requests: the first five returned HTTP 400 because they had no anti-forgery token, and the sixth returned HTTP 429. Those requests did not reach the contact action or send email. This confirmed the rate limit was working.

2. Honeypot: catch basic form-filling bots

A honeypot is a hidden input field used as a spam trap. This form includes an extra field named Website, positioned offscreen and removed from the keyboard and screen-reader flow. A real visitor does not see or fill it. Some simple bots scan a form and fill every field they find.

Visitor leaves hidden field blank ──► Normal validation ──► Resend sends the message
Bot fills hidden field ──► Server recognizes the trap ──► Discard message without emailing

If the hidden field contains text, the server quietly shows the normal success message but does not call Resend. This avoids telling a basic bot that it was detected. A more advanced bot can ignore the field, so the honeypot cannot stop every spammer.

When to add stronger filtering

The rate limit and honeypot are basic protections for this local project. If real abusive submissions continue, consider adding a CAPTCHA or a dedicated spam filtering service. CAPTCHA adds an extra step for visitors, so use it only if the lighter checks are not enough.
