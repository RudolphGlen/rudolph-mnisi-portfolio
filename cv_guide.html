Page 1: System Architecture Overview

Before implementing our database, the personal CV website operated purely on static views and a Resend contact form. To support a secure admin dashboard, we integrated ASP.NET Core Identity backed by a lightweight SQLite database.

[ Browser / Microsoft Edge ]
                │
                ▼ (HTTP Request: /Admin/Login)
[ Admin Controller ] ──(Verifies Password)──► [ SignInManager ]
                │                                │
                ▼                                ▼
[ SQLite app.db ] ◄──(Entity Framework Core)──┘

Core Components:

  • Admin Controller: Handles web requests for login and dashboard management.
  • SignInManager: ASP.NET Core's built-in cryptographic security layer for validating credentials.
  • SQLite (`app.db`): A serverless, self-contained database file storing encrypted user data locally.

Database Setup & EF Core Configuration

Page 2: Connecting C# to SQLite

Entity Framework Core (EF Core) acts as an Object-Relational Mapper (ORM), letting us write C# code instead of raw SQL queries to interact with our database.

1. Connection String (`appsettings.json`)

{
  "ConnectionStrings": {
    "DefaultConnection": "Data Source=app.db"
  }
}

2. Database Context (`Data/ApplicationDbContext.cs`)

The context inherits from `IdentityDbContext`, automatically provisioning tables for Users, Roles, Claims, and Logins.

using Microsoft.AspNetCore.Identity.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore;

namespace BeginnerMvc.Data
{
    public class ApplicationDbContext : IdentityDbContext
    {
        public ApplicationDbContext(DbContextOptions<ApplicationDbContext> options)
            : base(options)
        {
        }
    }
}

Migrations were then applied using terminal commands (`dotnet ef migrations add` and `dotnet ef database update`), successfully compiling the local binary file `app.db`.

Admin Credentials & User Secrets

Page 3: Keeping local credentials out of source files

The Admin account seeder reads its email and password from application configuration at runtime. For local development, provide these values with .NET User Secrets using the dotnet user-secrets command.

Configuration keys

  • AdminSettings:Email
  • AdminSettings:Password

Use dotnet user-secrets set to set each key on your development machine. Keep the actual values out of C# code, HTML guides, settings files, and source control. User Secrets are for local development; use your hosting provider's protected settings for a deployed site.

ASP.NET Core Identity hashes the password when it creates the account. The seeder needs the configured values only when it checks for or creates the initial Admin account.

Authentication & Future Roadmap

Page 4: Login Verification & Next Steps

When you log into your admin dashboard, the following sequence occurs:

Login Form Input ──► SignInManager ──► Matches Hashed Password in SQLite ──► Issues Auth Cookie ──► Admin Dashboard

Current Authentication Setup:

  • The Admin login uses ASP.NET Core Identity.
  • Admin credentials are read from configuration keys supplied with .NET User Secrets during local development, not embedded in code or HTML.
  • The seeder checks for the initial Admin account and creates it only when it is missing.

Next Steps for Portfolio Development:

  • Secure admin controllers using the `[Authorize]` data annotation.
  • Build CRUD operations to manage public website projects, education, and skills dynamically from the dashboard.
